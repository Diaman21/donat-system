# CLAUDE.md — карта проекта donat-system

> Этот файл загружается в контекст Claude в каждой сессии.

## 1. О проекте

**Цель.** Система управления закупкой донатов в мобильных играх. Оператор
закупает донаты через Apple Pay на iPhone. Главная задача — **выявить
оптимальные паттерны «разогрева» телефонов** и не «убивать» их ошибками,
фиксируя все данные в базу знаний для последующего анализа.

**Не цель.** Это не e-commerce, не магазин, не мульти-тенант SaaS. Это
внутренний инструмент маленькой команды (3 роли, ≤3 активных телефона).

## 2. Стек

| Слой | Технология | Назначение |
|---|---|---|
| БД | **Neon** (serverless Postgres) | Хранение данных, бесплатный план |
| ORM + миграции | **Drizzle ORM** | TypeScript-типы из схемы, миграции |
| Telegram-бот | **Node.js + TypeScript + grammY** | Оперативная работа всех ролей |
| Веб-аналитика | **Next.js (App Router) + TypeScript + Vercel** | База знаний, дашборды |

Один язык (TS) во всём проекте — типы из Drizzle-схемы, общий tooling.

**Почему Neon, а не Supabase:** Neon бесплатен, это чистый Postgres —
наши триггеры, RLS и индексы работают без изменений. Supabase-специфичные
фичи (Auth, Storage, Realtime) нам не нужны.

## 3. Роли

| Роль | Что может |
|---|---|
| 🛍️ **customer** (заказчик) | создаёт заказ: игр.аккаунт + сумма |
| 👨‍💼 **operator** (оператор) | берёт заказ, привязывает телефон по 4 цифрам IMEI, фиксирует результат каждой покупки |
| 🛡️ **moderator** (модератор) | всё + редактирование, управление телефонами/категориями, веб-аналитика |

## 4. Ключевые правила (закреплены в БД)

- **≤3 активных телефона** (триггер `enforce_max_active_phones`)
- **Уникальность IMEI только среди активных** телефонов (частичный unique index) —
  умершие телефоны с тем же IMEI остаются в истории
- **💀 `long` → телефон умирает навсегда** (триггер `handle_long_result`):
  status → `dead`, `died_at` фиксируется, `death_purchase_id` ссылается на убийцу
- **Разогревочные покупки без заказа** — `purchases.order_id` nullable
- **RLS включён везде**; бот подключается напрямую через Postgres (DATABASE_URL)
  с полными правами; политики для веба добавим на этапе фронта

### Результат покупки
- ✅ `done` — выполнено
- ⚠️ `support` — короткая ошибка (повтор на следующие сутки)
- 💀 `long` — телефон умирает навсегда (берём следующий)

### Типы закупок (расширяемо, в `purchase_categories`)
- `game_donate`: $2 / $30 / $100
- `vk_votes`: $4 (логика разогрева — позже)

## 5. Архитектурные решения

- **Один заказ → много покупок.** Заказ может разбиваться на несколько
  фактических покупок (повторы после `support`, переносы на новый телефон).
- **Покупки — ядро базы знаний.** Каждая покупка — точное время + телефон +
  сумма + результат. Этот лог потом анализируем для выявления паттернов разогрева.
- **Циклическая ссылка** `phones.death_purchase_id → purchases.id` — храним
  «какой именно покупкой убит телефон» для post-mortem анализа.
- **Категории расширяемы.** `purchase_categories.warmup_config jsonb` — здесь
  гипотезы разогрева, можно менять без миграций.
- **Drizzle вместо сырого SQL в коде.** Схема описана в `bot/src/db/schema.ts`,
  типы генерируются автоматически, миграции через `drizzle-kit`.

## 8. Рабочий процесс (важно)

1. **План → ждать «ок» → код.** Никаких изменений кода без явного подтверждения.
2. **Переключай на Opus** перед критичными задачами: миграции, каркасы,
   RLS, деплой. Claude напоминает об этом сам.
3. **SQL руками для схемы.** Структурные изменения БД — через Neon SQL Editor
   или `drizzle-kit push`. Claude не применяет DDL автоматически.
4. **Файлы целиком** при показе изменений — без «...остальное без изменений».
5. **После каждого шага:** коммит → push → отчёт.
6. **Простота важнее красоты.** Не делаем того, о чём не просили.
7. **Коммиты на русском**, с соавторством Claude.
