## 1. О проекте

Система учёта закупки донатов в мобильных играх через Apple Pay на iPhone.
Главная задача — **найти «зелёный коридор»**: сколько и на какие суммы (€) можно
покупать на телефоне, **не получив ошибку**, чтобы телефоны жили дольше.
Анализируем **покупки** (сумма €, время, телефон, результат), а не заказы.
**Валюта — евро (€) везде.** Не цель: магазин, SaaS, работа с заказчиками.
Команда: владелец @Boris_donat (moderator) и оператор @timka_mir (operator).

## 2. Модель работы — бот = логгер закупок (в личке)

- **Ввод закупки** (всё кнопками): телефон → категория (только «🛒 Без заказа») →
  игра (только танки; из заказа пропускается) → сумма € (кнопки по игре + «✏️ Другая») →
  результат ✅/⚠️/🔐/💀 → заметка → подтверждение → **выбор интернета 📶/📡 записывает**.
  Везде ❌ Отмена и `/cancel`. После записи — подсказка «когда можно следующую» (танки).
- **Телефон:** 4 цифры IMEI + метка → «▶️ В работу» (≤3 активных, триггер БД) или
  «🧰 В подготовленные» (резерв вне лимита). Модель аппарата берётся из метки.
  «☎️ Телефоны» — карточки через линию: название жирным, последняя покупка, «⏳ €100 — через…».
- **⏰ Напоминания о слотах под €100** (с 19.10.2026): в тему 📥 Заказы с тегами команды,
  только при открытых заказах, 09:00–24:00 МСК, одно на слот (`slots.ts`, `slot-notify.ts`).
  Дёргает **cron-job.org** каждые 10 мин → `/api/cron-slots` с отдельным `SLOTS_SECRET`
  (кроны Vercel Hobby — раз в сутки). Нет секрета — будильник выключен.
- **Заказы** (`order_queue`) — главный вход: `📥 Заказы`, `✅ Выполнить` запускает ту же
  цепочку закупки (короче: без категории и игры). Завести: кнопкой, `/order <текст>`
  (работает и в группе), `/order`. Заказ может требовать несколько закупок
  («Орден + Банки» = 2×€30): состав распознаёт `order-parse.ts`, оператор подтверждает;
  закрывается, только когда успешных ≥ `items.total`. ⚠️/💀/🔐 счётчик не двигают.
  Сумма из заказа **не подставляется** — точность важнее одного нажатия.
  Прайс: Furious — орден €30 · банки €30 · прем год €105; Massive — всё €100.
  **Один заказ = одна игра.**
- ⚠️ `pendingOrderId` сбрасывается при `/cancel` и входе в «🛒 Без заказа».
  ⚠️ Кнопку «Без заказа» не убирать: разогрев €2 и вся ВК идут без заказа.
  ⚠️ `orders.ts` НЕ импортирует `purchase.ts` (циклический импорт на Vercel-ESM).
- **Отчёты:** `/stats` · `/period` · `/corridor` · `/learn` · `/vk` · `/find` · `/recent` ·
  `/history` · ↩️ удалить последнюю (с воскрешением телефона) · `/export` (модератор).
- **💳 Бюджет на карте** (`/budget`, с 10.10.2026) — по нему решают, когда выкатывать.
  Сумму вписывают руками (оба), ✅ вычитаются сами, возврат выкаченного телефона (все его
  ✅) прибавляется сам через 48 ч; поправка возврата руками. Строка — после ✅ покупки,
  после вывода, в сводке 12:00, `/stats` и `/report`; ниже €250 даже с возвратами — 🔴 и
  кандидат на выкат.
- **Группа «Pattern_analyst 🧮»** — супергруппа с темами: 📊 Сводки (сводка 12:00,
  `/report`, итоги циклов) · 🗄 Бэкапы (12:05) · 📥 Заказы. Обычные сообщения в группе
  заказами не становятся. Отдельный канал не заводим: там @упоминание не пингует.

## 4. Правила данных (закреплены в БД)

- ≤3 активных телефона (триггер). IMEI уникален только среди активных.
- Повтор 4 цифр IMEI при добавлении — **предупреждение**, сверка с резервом и умершими
  (`phone-dup.ts`); совпал с резервом — «▶️ Взять из резерва» вместо новой записи.
- **💀 long → телефон `dead`, причина `'error'`; 🔐 verify → `dead`, причина `'verify'`**
  (триггер `handle_long_result`). Ручной вывод «☠️ Вывести» → `'forced'` — искусственный,
  в коридор как порог не считать. Разбор причины — только через `death.ts`.
- **Деньги и голоса — только по ✅** (`money.ts`): ⚠️/💀/🔐 не списывают. Счёт покупок —
  по всем попыткам (это нагрузка на телефон).
- **Дубль опаснее потери.** У каждой покупки ключ идемпотентности (`idem.ts`, миграция
  `0015`): повторная доставка апдейта и двойное нажатие не создают вторую строку.
  Оператору при ошибке — только «запись могла пройти, проверь /recent», никогда
  «попробуй заново». `purchases` после записи не обновляется (нет `update(purchases)`).
- **Баланс карты не хранится, а вычисляется** (`card-calc.ts`, миграция `0017`): последняя
  вписанная сумма − ✅ после неё (по `created_at`) + наступившие возвраты. В `card_ledger` —
  только вписанные суммы и поправки возвратов (одна на телефон). Счётчик не заводить.
- Удалить покупку — только ↩️ свою последнюю; телефон — только из резерва без покупок.
- RLS включён на всех 7 таблицах, **политик нет** — RLS сейчас ничего не защищает
  (бот ходит владельцем с `bypassrls`). Не писать в документах «RLS защищает данные».
- Известное исключение: …1388 — строка 💀, но причина `forced` (решение владельца).

### Результат покупки — точные диалоги Apple (интерфейс на немецком)
- ✅ `done` — прошла.
- ⚠️ `support` — **телефон жив**, отлёжка ~сутки: «**Dein Kauf konnte nicht abgeschlossen
  werden.** Für Unterstützung wende dich an den iTunes Support…» (`OK`).
- 💀 `long` — **телефон мёртв навсегда**, убивает само появление окна: «**Bestätigung.**
  Ich bestätige, dass ich diesen Kauf nicht mehr stornieren kann, wenn ich diesen
  In-App-Kauf innerhalb von **vierzehn Tagen**… lade oder verwende.» (`Abbrechen`/`Kaufen`).
  Строка 💀 — попытка, деньги не ушли.
- 🔐 `verify` (с 06.10.2026) — «**Покупка не завершена.** Отправьте запрос на проверку
  в службу поддержки Apple.» (`Дальше`/`Не сейчас`; немецкий оригинал снять при
  следующем случае). Телефон выкатывают, бюджет возвращают. В расклад коридора
  **не входит** (там только 💀). **Случаев 5 за 06–14.10**, до 06.10 — ни одного
  (0 из 82 крупных с протокола, после — 5 из 17). Модели разные (13, 15, 15/16 Pro Max),
  3 из 5 на Wi-Fi, партии разные, 4 из 5 — при чистом протоколе коридора; заказ после
  🔐 проходит на другом телефоне. ❌ Гипотеза «базовые 13 + мобильный + одна партия»
  опровергнута. Темп покупок 🔐 не объясняет; похоже на внешнюю перемену с 06.10.
  Динамика — `/learn`, раздел 7 (`verify-trend.ts`); разбор — `docs/history.md`.

### Гигиена ввода
Вбивать сразу после покупки (`purchased_at` = время записи). Мультизакуп с ошибкой
пишется как (N−1)×✅ + 1 ошибка; строки серии имеют одно время — считать серию одним
событием. Правка данных задним числом — одной транзакцией со сверкой контрольных
сумм, реальное время ввода остаётся в `created_at`.

### Типы закупок
- `game_donate`: **Massive** €2 (разогрев, только здесь) и €100 · **Furious** €30 и €105
  (€105 — один раз на телефон, бот подсвечивает).
- `vk_votes`: 10 гол/€0.99 · 18/€1.99 · 28/€2.99 · 40/€3.99. **ВК на паузе** с конца
  июня 2026 (Apple заблокировали приложения). Всегда заказ, не разогрев.

### Три коридора
Танки и ВК — на одних телефонах, но методики разные: ищем коридор 🎮 танков,
🗳 ВК и 📱 суммарный (телефон умирает один раз от общей нагрузки). Смешанные
смерти годятся только для суммарного.

## 5. Рабочий протокол танков (действует)

1. **Разогрев ровно 2 дня**, €2 через Massive, одна в сутки.
2. **Дальше €100/€105, одна покупка в сутки, интервал 22–28 ч.** Слот в сутках один —
   сотня даёт втрое больше тридцатки. Длиннее 36 ч безопасно, но теряет слоты.
3. **Всегда Wi-Fi** (на крупных мобильный ~24% плохих исходов против ~5% у Wi-Fi).
4. **Полные 14 дней**, вывод бюджета — когда прошло 14 суток (предупреждение с 12-х).
5. **Правило безопасности:** можно, если **интервал ≥ 20 ч ИЛИ сумма ✅ за 24 ч < €120**,
   **И на не-Pro интервал ≥ 10 ч**. Опасная клетка (<20 ч и ≥€120) — около 40% смертей.
   2–3 тридцатки в сутки — норма; четвёртая (= €120) — смерть.

Константы — `interval.ts` (`DANGER_EUR`, `CORRIDOR_MIN_H`, `MIN_GAP_WEAK_H`, `WARMUP_DAYS`,
`WITHDRAW_DAYS`, `WARN_FROM_DAY`). Стадию вывода решает ОДНА функция `withdrawStage`
(сводка, подсказка и аномалии). Граница €106–119 не изучена. Протокол с 13.08.2026:
до 14-го дня доживает ~73% телефонов против ~30% до него. Полные таблицы — `/corridor`,
история их появления — `docs/history.md`.

**Помнить, чтобы не воскресить:** ❌ «телефон вырабатывает ~€245», ❌ «потолок €400–550»,
❌ «убивает сумма покупки», ❌ «никогда вторую покупку за день», ❌ «чем реже, тем лучше»
(оптимум ~24 ч). ⚠️ Смерти бывают и на €2 (…0524, …7057 — с внешней причиной).
ВК-гипотеза до паузы: ~800 голосов/день безопасно, два дня по 1000 подряд = смерть
(один чистый случай). **Тон отчётов:** пустой слот — не «упущенная выгода» (чаще не было
заказа), простой — факт и цена, без упрёка.

## 6. Обучение системы

- **Аномалии** (`anomaly.ts`): 🔴 danger / 🟡 observation / ℹ️ note — не смешивать.
  Отклонение называется после покупки как «засчитано», не «накосячил». ВК не проверяем.
- **Зоны за границами и правила** — одно определение в `zones.ts` (с датами фиксации).
  При 30 чистых наблюдениях в зоне сводка зовёт **обсудить** сдвиг; бот границу сам
  не двигает никогда.
- **`/learn`:** правила вне выборки, зоны Pro/не-Pro, выживаемость (Каплан–Мейер),
  интернет, ранние боевые, журнал подсказок, динамика 🔐 по неделям. Проценты — с 95%
  диапазоном (Уилсон).
- **Журнал подсказок** `advice_log` (миграция `0016`): коды отклонений (`AnomalyCode`,
  **не переименовывать**), с какого часа можно €30/€100, версия правил.
- ⚠️ **Никаких вшитых чисел в текстах оператору** — тест-страж в `anomaly.test.ts`.
- ⚠️ **Проверочные числа — только через `attempts()`** (`corridor.ts`): интервал — от
  покупки ЛЮБОЙ категории, сумма окна — ✅ танки за (t−24 ч, t]. Свой SQL с другим
  определением однажды «опроверг» верные цифры. Два расходящихся расчёта = разные
  определения, а не «прав второй».

## 7. Правила кода

- Фиксированные наборы — `Record<Тип, …>`, не тернарники. Условия — через «когда делать»
  (`result === 'done' || result === 'support'`), не «когда нет» (`!== 'long'`): новое значение
  тогда попадает в безопасную ветку.
- Время и календарь МСК — **только** `format.ts` (`cycleDayMsk`: день 1 = день первой покупки).
- Тесты — только чистая логика без `db/client.ts`/`config.ts`; страж `test-hygiene.test.ts`.
  `npm test` (node --test + tsx), **182 теста**; `restore.test.ts` поднимает миграции в PGlite.
- Нигде нет `select()` без проекции по `purchases` — удаление колонки не ломает деплой.
- Блоки сводки — в одном `Promise.all` (таймаут функции = единственная тихая потеря).
- Vercel: импорты с `.js`, `webhookCallback(..., 'https')`, `vercel.json` формата
  `functions`, Node закреплён `engines: 24.x`, сессии в БД.
- Локальный запуск — только с `TELEGRAM_BOT_TOKEN_DEV` (база при этом боевая!).
- Бэкап (12:05, JSON всех таблиц + CSV) восстанавливается **скриптом**
  `npm run restore-drill` — проверено один в один. Откат Neon «на момент» — всего 6 ч.

## 10. Рабочий процесс

1. **План → ждать «ок» → код.** Без явного подтверждения код не меняется.
2. **Переключай на Opus** перед критичными задачами (миграции, RLS, деплой, каркасы).
   Claude напоминает об этом сам.
3. **Схема БД — только миграцией:** файл `supabase/migrations/000N_*.sql` → показать SQL →
   **спросить разрешение отдельно** → применить. Claude НЕ применяет DDL без разрешения.
   Панель Neon у владельца заблокирована, поэтому миграции `0008`, `0011`–`0017`
   применил Claude напрямую через `DATABASE_URL` — каждый раз с отдельного «да».
   Правка ДАННЫХ — тоже только по просьбе, транзакцией со сверкой контрольных сумм.
4. **После шага:** `npm run typecheck` + `npm test` → удалить `bot/tmp-*.ts` → коммит в
   `main` → push → дождаться CI и деплоя → отчёт.
5. **Простота важнее красоты.** Найденное попутно — не чинить молча, а сообщить и
   записать в `TODO.md`.
6. **Коммиты на русском**, с соавторством Claude.
7. Подробные разборы — в конец `docs/history.md` с датой; сюда — только вывод.
