## 1. О проекте

**Цель.** Система управления закупкой донатов в мобильных играх. Оператор
закупает донаты через Apple Pay на iPhone. Главная задача — **найти
«зелёный коридор»**: сколько и на какие суммы ($) можно делать покупок на
телефоне, **не получив ошибку**, чтобы телефоны жили максимально долго и
давали закупать. Все покупки фиксируются в базу знаний для анализа.

**Что анализируем.** Не заказы, а **покупки**: сумма в $, частота,
последовательность сумм во времени по каждому телефону — до ⚠️/💀.
Реальная стоимость в долларах — главная метрика нагрузки на телефон.

**Не цель.** Это не e-commerce, не магазин, не мульти-тенант SaaS. Это
внутренний инструмент маленькой команды (3 роли, ≤3 активных телефона).

## 1.1. Модель работы (РЕШЕНО — бот = логгер закупок)

Бот **не** ведёт доску заказов и не общается с заказчиками. Заказы и общение
команда ведёт сама, вручную (как и раньше). Бот делает одно: оператор в **личке**
вбивает каждую закупку → бот копит данные в БД и (далее) выдаёт аналитику.

**Привязка телефона:** оператор вводит 4 цифры IMEI + метку. ≤3 активных (триггер БД).

**Ввод закупки (ядро, в личке, пошагово, всё кнопками):**
1. Телефон (выбор из активных)
2. Категория (game_donate / vk_votes)
3. Игра (кнопки: Massive / Furious / без игры)
4. **Сумма $** (кнопки из denominations категории + «Другая» текстом) — метрика нагрузки
5. Результат: ✅ done / ⚠️ support / 💀 long
6. Заметка (опц., кнопка 📝) → **подтверждение** (сводка + ✅ Записать)
→ запись в `purchases` (operator_id = кто вбил, время — авто). При 💀 телефон → `dead` (триггер).
Везде есть ✖️ Отмена и `/cancel`.

**Просмотр/аналитика:** `/stats` (периоды сутки/неделя/всё), `/recent` (последние),
`/history` (таймлайн телефона с заметками), ↩️ удалить последнюю (с воскрешением при откате 💀),
post-mortem при смерти, `/export` (CSV, модератор).

**Группа «Pattern_analyst 🧮»:** команды-просмотр (`/stats /phones /recent /report`) +
авто-сводка по расписанию (Vercel Cron, ежедневно 12:00 МСК). Бот игнорит обычные сообщения в группе.

> Заказчики, канал-доска, карточки, комментарии — НЕ делаем (осознанно убрали как
> «лишние переменные»). Цель — чистые данные о покупках для «зелёного коридора».

## 2. Стек

| Слой | Технология | Назначение |
|---|---|---|
| БД | **Neon** (serverless Postgres) | Хранение данных, бесплатный план |
| ORM + миграции | **Drizzle ORM** | TypeScript-типы из схемы, миграции |
| Telegram-бот | **Node.js + TypeScript + grammY** | Логгер закупок, аналитика |
| Хостинг бота | **Vercel** (serverless, webhook) | Бот 24/7, бесплатный Hobby |
| Веб-аналитика | **Next.js + Vercel** (позже) | База знаний, дашборды |

Один язык (TS) во всём проекте — типы из Drizzle-схемы, общий tooling.

**Почему Neon, а не Supabase:** Neon бесплатен, это чистый Postgres —
наши триггеры, RLS и индексы работают без изменений. Supabase-специфичные
фичи (Auth, Storage, Realtime) нам не нужны.

## 3. Роли

| Роль | Что может |
|---|---|
| 🛍️ **customer** | роль по умолчанию при `/start` = **БЕЗ доступа**. Просьба передать ID модератору. (Заказчики в системе не работают — роль осталась в enum, но не используется.) |
| 👨‍💼 **operator** (оператор) | привязывает телефон по 4 цифрам IMEI, вбивает закупки (телефон + игра + сумма $ + результат) |
| 🛡️ **moderator** (модератор) | всё + (далее) управление ролями/телефонами, веб-аналитика |

Роль назначается вручную: `bot/src/db/set-role.ts <telegram_id> <role>`.

## 4. Ключевые правила (закреплены в БД)

- **≤3 активных телефона** (триггер `enforce_max_active_phones`)
- **Уникальность IMEI только среди активных** телефонов (частичный unique index) —
  умершие телефоны с тем же IMEI остаются в истории
- **💀 `long` → телефон умирает навсегда** (триггер `handle_long_result`):
  status → `dead`, `died_at` фиксируется, `death_purchase_id` ссылается на убийцу,
  `death_reason` = `'error'` (ошибка Apple = достиг предела)
- **Причина смерти** (`phones.death_reason`): `'error'` — ошибка Apple (через 💀),
  `'forced'` — вынужденный вывод оператором (возврат бюджета). ⚠️ Для аналитики
  «зелёного коридора» `forced`-смерти НЕ считать порогом — они искусственные.
- **Разогревочные покупки без заказа** — `purchases.order_id` nullable
- **RLS включён везде**; бот подключается напрямую через Postgres (DATABASE_URL)
  с полными правами; политики для веба добавим на этапе фронта

### Результат покупки
- ✅ `done` — выполнено
- ⚠️ `support` — короткая ошибка (повтор на следующие сутки)
- 💀 `long` — телефон умирает навсегда (берём следующий)

### Типы закупок (расширяемо, в `purchase_categories`)
- `game_donate`: $2 / $30 / $100
- `vk_votes`: $4 (и мелкие)

### ⚠️ Принцип анализа: телефон общий, нагрузка суммарная
Танки и ВК делаются на ОДНИХ телефонах. «Зелёный коридор» телефона = **суммарная
нагрузка** (танки + ВК вместе) — её и анализируем для порога смерти. Раздельная
разбивка (🎮 Танки / 🗳 ВК) — чтобы видеть вклад каждой методики. Считаем И вместе, И раздельно.

### ⚠️ Правило разогрева (важно для аналитики)
- **`game_donate` $2 — ВСЕГДА разогрев телефона**, не заказ (заказов на $2 не бывает).
- **`game_donate` $30 / $100 — реальные закупки** (боевая нагрузка по заказам).
- **`vk_votes` — всегда заказы** (включая мелкие покупки), это НЕ разогрев.
- Различается аналитикой по `category` + `amount` (отдельное поле не нужно). При поиске
  «зелёного коридора» разогрев ($2) и боевые закупки учитываются с этим контекстом.

### 🔥 Методика прогрева (стартовые гипотезы в `warmup_config`)
Записаны раздельно по категориям. Правка: `bot/src/db/set-warmup.ts` (методики в коде, перезапустить).
- **game_donate (Massive/Furious):** 2–3 дня по €2 (разогрев) → затем €30 и €100.
- **vk_votes:** ВК ~2 недели/мес. Номиналы: 10 гол/€0.99, 18/€1.99, 28/€2.99, 40/€3.99.
  День 1: серия 4 покупки по 40 голосов (€3.99), повторить 2–3 раза с интервалом
  в несколько часов; далее лимит растёт. **Методика ВК отличается от игр.**
- Цель — выявить/уточнить точный цикл и коридор по данным (анти-цель: не вычислять раньше данных).

## 5. Архитектурные решения

- **Покупки — ядро базы знаний.** Каждая покупка — точное время + телефон +
  сумма $ + результат + игра. Этот лог анализируем для «зелёного коридора».
  `purchases.order_id` всегда NULL (заказов в боте нет — модель логгера).
- **Циклическая ссылка** `phones.death_purchase_id → purchases.id` — храним
  «какой именно покупкой убит телефон» для post-mortem анализа.
- **Категории расширяемы.** `purchase_categories.warmup_config jsonb` — здесь
  гипотезы разогрева, можно менять без миграций. Закупка по умолчанию = `game_donate`.
- **Drizzle только для типобезопасных запросов**, НЕ для миграций. Схема в
  `bot/src/db/schema.ts` — зеркало применённого SQL. Миграции схемы — руками
  (см. раздел 8). `bot/src/db/*.ts` содержит утилиты: `check`, `set-role`, `users-list`.

## 8. Рабочий процесс (важно)

1. **План → ждать «ок» → код.** Никаких изменений кода без явного подтверждения.
2. **Переключай на Opus** перед критичными задачами: миграции, каркасы,
   RLS, деплой. Claude напоминает об этом сам.
3. **SQL руками для схемы.** Структурные изменения БД — новый файл
   `supabase/migrations/000N_*.sql`, который пользователь запускает в Neon SQL Editor.
   Claude НЕ применяет DDL автоматически. После — обновить `bot/src/db/schema.ts`.
4. **Файлы целиком** при показе изменений — без «...остальное без изменений».
5. **После каждого шага:** коммит → push → отчёт.
6. **Простота важнее красоты.** Не делаем того, о чём не просили.
7. **Коммиты на русском**, с соавторством Claude.
